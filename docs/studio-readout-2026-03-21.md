# 工作室开发总览（截至 2026-03-21 早晨）

> 目标：把 `survivor-demo` 从立项到昨晚的主要开发动作整理成一份**人能快速读懂**的版本，方便主理人快速了解：已经做了什么、现在处在哪、还缺什么、今天准备怎么推进。

---

## 1. 一句话总览

`survivor-demo` 已经从“能跑的原型”推进到一个**可网页试玩、可手机竖屏体验、具备基础交付链路和可追溯文档体系的 Web demo**。

昨晚工作的重心，不再是单纯堆新功能，而是把项目继续往以下四个方向收口：

1. **更能交付**：Web 交付链路、受控托管、验收说明、对外分享话术继续补齐
2. **更适合手机试玩**：竖屏 HUD、提示避让、暂停/结算可读性继续优化
3. **更像完整作品**：地图存在感、区域气质、界面结构、UI 落地规划继续加强
4. **更方便后续协作**：把设计方向、Godot 节点映射、组件规划和工作日志继续写成文档

---

## 2. 已完成的开发主线

### A. 核心玩法闭环已完成
已经具备：
- 玩家移动
- 自动攻击
- 经验掉落与升级成长
- 三类敌人（基础 / 快速 / 重装）
- 精英波次
- 3 分钟短局目标
- 受击、击杀、升级等基础反馈
- 暂停 / 失败 / 通关结果面板

这意味着项目已经不再是“技术验证空壳”，而是一个有完整短局节奏的可玩 demo。

### B. Web 试玩链路已基本打通
已经具备：
- `builds/web-release/` 验收基线
- `builds/web/` 压缩交付版
- `builds/pages-deploy/` 旧备份发布目录
- `release_guard.sh` / `controlled_web_guard.sh` / `pages_release_guard.sh` 等验证脚本
- 本地可控预览与受控托管模板
- 发布验收、部署、故障排查、分享话术等文档

这意味着项目已经具备“工程上可以交付”的基础，而不是只能在本机编辑器里演示。

### C. 手机竖屏试玩能力已补上
已经做过多轮修复与优化：
- 手机竖屏布局适配
- 摇杆与闪避按钮不再轻易被 HUD 挡住
- 小屏字体和触控区放大
- HUD 信息分层重排
- 顶部播报、右上状态签、底部操作带重新避让
- 暂停 / 结算界面在手机上可读性明显增强

昨晚又进一步收掉重复信息，把真正关键的数据（命火 / 军令 / 波次）提权。

### D. 中文显示问题已修复
此前网页端中文会乱码/方块，已经通过接入字体资源和覆盖逻辑修掉。

### E. 地图“空底板”问题已显著改善
已经新增程序化地图表现模块，并进一步增强：
- 地表底纹
- 路痕 / 碎石 / 荒地 / 草痕
- 中景锚点（石碑、经幡、残柱、小树等）
- 区域气质与节奏感

这让“角色在移动，但场景像没动”的问题得到明显缓解。

### F. UI / 视觉设计方向已从抽象想法推进到可落地文档
已经补齐：
- 西游记古风 Q 版方向板
- HUD / 结算页线框文档
- AI 出图提示词包
- UI 可复用组件实施计划
- Godot 场景节点映射方案

这意味着 UI 线已经不只是“口头说想做古风”，而是已经有了可继续执行的落地图纸。

## 3. 昨晚重点做了什么

### 3.1 Web 交付继续收口
昨晚继续把“怎么交付给别人试玩”往前推进，补了：
- controlled web 自管交付方案
- 用户侧验收说明
- 对外发送试玩链接标准消息模板
- 故障排查手册
- 临时验收运行手册
- Godot 场景与 UI 的映射文档

### 3.2 手机端体验继续优化
昨晚对手机竖屏又做了几轮针对性优化：
- 压缩战斗态 HUD
- 隐藏重复信息块
- 缩短临时提示驻留时间
- 提高关键数值优先级
- 强化竖屏 smoke 测试，防止后续回归

### 3.3 地图表现继续增强
在已有程序化地图存在感模块基础上，进一步增强：
- 区块化地表语汇
- 更明显但克制的层次
- 中景锚点节奏
- 区域偏好的装饰组合

### 3.4 UI 文档继续从“方向”推进到“实装准备”
补了：
- 可复用组件规划
- HUD / 结算页到 Godot 现有节点的映射方案
- 面向后续真正实装的优先顺序

## 4. 当前项目状态判断

### 4.1 从玩法上看
已经够你体验、够别人试玩、也够做一轮产品/视觉判断。

### 4.2 从工程上看
已经具备“可导出、可本地托管、可做对外分享”的基础，但**版本冻结还没彻底收死**。

### 4.3 从观感上看
已经不再是纯技术原型，但距离“第一眼就像正式小作品”还差最后一轮视觉与信息层级收口。

## 5. 当前还没开发完 / 还没真正收口的任务

### P0：必须优先收口
1. **版本冻结 / 口径统一**
   - 把源码、场景、构建产物、文档统一成一个清晰版本号
   - 避免“当前验过的版本”和 Git 提交号不是同一个东西

2. **今天 9 点交付版准备**
   - 产出一份你能直接点开的试玩链接
   - 确保链接对应的是可玩的当前版本，而不是旧版本

### P1：已做很多，但还没最终落版
3. **UI / HUD 最终落版**
   - 重点不是再发散，而是把已经做过多轮的 HUD、状态签、暂停/结算页收成最终体验版本

4. **正式视觉资产最小替换包**
   - 主角
   - 三类敌人
   - 基础按钮 / 面板 / 图标
   - 结果页装饰

5. **正式托管回归**
   - 需要对最终分享链接再做一次完整回归，确认不是“本地能跑、线上出问题”

### P2：还没真正开始或只做了方向研究
6. 更多武器分支
7. 音效体系
8. 更重的演出反馈
9. Boss / 更完整敌人层次

## 6. 今日建议的开发优先级

### 今日目标（强约束）
**09:00 前给主理人一个可玩的版本链接。**

### 今日最合理的顺序
1. 先做 **P0 版本收口**
2. 跑最小必要验证，确认当前版本确实可玩
3. 产出试玩链接
4. 再继续做 UI/HUD 最终落版或 9 点版本后的定点优化

### 为什么今天不应该继续无上限加新功能
因为当前最大的风险不是“内容太少”，而是：
- 版本口径还没完全收死
- 试玩链接必须稳定
- 你今天要体验，所以**先可玩、可交付、可复现**比继续加功能更重要
