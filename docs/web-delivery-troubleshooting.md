# Web 交付故障排查手册

> 目标：把 survivor-demo 当前 Web 交付里最常见的几类问题——黑屏、慢加载、旧缓存、临时隧道失效——收口成一份可执行的排查清单，降低临时验收期间的沟通与试错成本。

> 适用范围：`builds/web/` + `scripts/serve_controlled_web.py` + 受控 Nginx / 临时外链 / Pages 备份链路。

## 1. 先做分类，不要上来就叫“黑屏”
临时验收时最容易浪费时间的情况，是把完全不同的问题都叫成“黑屏”。

建议先分成 4 类：

1. **真黑屏**
   - 页面能打开，但只有空白/纯底色，几乎没有有效提示
2. **慢加载**
   - 有加载页或阶段提示，但长时间卡在某一阶段
3. **旧缓存**
   - 页面能开，但像旧版本、旧 UI、旧文案，或刚修的 bug 看起来没生效
4. **隧道失效 / 链路失效**
   - 直接打不开、502/504、连接超时、时好时坏

先分类，后排查，效率会高很多。

## 2. 通用排查顺序
不管用户反馈哪一类问题，先按这个顺序走：

1. **本地受控守卫是否通过**
   ```bash
   ./tests/smoke/controlled_web_guard.sh
   ```
2. **本机受控服务能否正常打开**
   ```bash
   python3 scripts/serve_controlled_web.py --port 18084
   ```
3. **外链健康检查是否正常**
   ```bash
   curl -fsS https://your-domain/healthz
   ```
4. **外链头部是否仍符合 controlled web 口径**
   ```bash
   ./tests/smoke/verify_controlled_web_remote.sh https://your-domain
   ```
5. **再让用户做浏览器侧动作**
   - 刷新
   - 强刷
   - 无痕模式
   - 换浏览器

核心原则：

**先排服务端与交付链路，再排用户设备。**

## 3. 问题一：黑屏

### 3.1 典型表现
- 打开链接后页面空白
- 看不到明确错误提示
- 或者只有页面壳层，但游戏区始终不进入

### 3.2 优先怀疑什么
按优先级排：
1. `index.wasm` MIME 不对
2. `gzip` 没生效或头被外链吃掉
3. `index.html` / `index.js` / `index.wasm` / `index.pck` 版本不一致
4. 浏览器命中了旧缓存
5. 临时外链中间层篡改或丢失头部

### 3.3 快速检查项
```bash
./tests/smoke/verify_controlled_web_remote.sh https://your-domain
```

重点看：
- `index.wasm` 是否有 `Content-Type: application/wasm`
- `index.wasm / index.js / index.pck` 是否有 `Content-Encoding: gzip`
- 是否有 `Vary: Accept-Encoding`
- `index.html` 是否为 `no-cache, max-age=0, must-revalidate`

### 3.4 本机对照法
如果外链黑屏，但本机 `http://127.0.0.1:18084/index.html` 正常：
- 优先判断为**外链或代理层问题**
- 不要立刻重导出游戏

如果本机也黑屏：
- 再回头检查 `builds/web/` 是否被错误覆盖
- 重新跑 `./tests/smoke/controlled_web_guard.sh`

### 3.5 处理建议
- 先修 header / gzip / cache 口径
- 再让用户无痕模式重试
- 如果外链层无法保留这些头，直接换链路，不要死磕

## 4. 问题二：慢加载

### 4.1 典型表现
- 页面不是纯白，但长时间停在加载页
- 常见反馈是“好像没死，但一直进不去”

### 4.2 当前项目的已知事实
- 当前完整版 `index.wasm` 原始体积较大
- 这类问题不一定是崩溃，更可能是：
  - 网络慢
  - 临时隧道吞吐不稳
  - 外链没正确走 gzip
  - 某个资源请求失败后浏览器一直等待

### 4.3 优先看什么
用户反馈时，先问清：
- 卡在阶段 1/3、2/3 还是 3/3
- 是否只在蜂窝网络下复现
- 刷新一次后是否改善
- 同一链接在另一台设备是否正常

### 4.4 排查重点

#### 卡在阶段 1/3：请求 / 下载 wasm
优先怀疑：
- `index.wasm` 太大且没走 gzip
- 临时外链带宽不足
- 某网络环境对大文件拉取不稳定

检查：
```bash
./tests/smoke/verify_controlled_web_remote.sh https://your-domain
```

#### 卡在阶段 2/3：请求 / 下载 pck
优先怀疑：
- `index.pck` 请求失败或很慢
- 代理层对 Range / 缓存 / gzip 处理异常

#### 卡在阶段 3/3：初始化运行时
优先怀疑：
- 前面资源虽然 200 了，但头不对
- 资源版本不一致
- 浏览器命中旧缓存

### 4.5 处理建议
- 先确认是不是 `gzip` 头丢了
- 让用户刷新一次
- 仍慢就切更稳的网络或换链路
- 如果临时隧道吞吐明显不稳，直接回退到备份链路或改用临时 Nginx 站点

## 5. 问题三：旧缓存 / 看起来没更新

### 5.1 典型表现
- 页面能打开，但 UI 还是旧的
- 文案、布局、交互像上一个版本
- 明明说修复了，用户端还是复现

### 5.2 根因特点
当前 Godot Web 运行时文件名是固定的 `index.*`，所以旧缓存是高概率问题。

本项目当前口径已经专门做了防护：
- `index.html`：`no-cache, max-age=0, must-revalidate`
- `index.js / index.wasm / index.pck`：`public, max-age=600, must-revalidate`

如果又出现“像没更新”，通常说明：
- 某条链路把缓存头改坏了
- 用户端已有旧缓存
- 外链/CDN 返回的不是最新目录

### 5.3 排查动作
1. 先跑：
   ```bash
   ./tests/smoke/verify_controlled_web_remote.sh https://your-domain
   ```
2. 让用户：
   - 强刷
   - 无痕模式
   - 换浏览器
3. 确认你发出去的链接是否就是最新那条
4. 确认临时外链指向的本机端口/目录没有切错

### 5.4 处理建议
- 只要怀疑旧缓存，**优先让用户开无痕模式**，这是最快验证法
- 如果无痕能好，基本就不是游戏逻辑问题，而是缓存或 CDN 问题
- 不要轻易重新导出覆盖，先确认是不是链路没切到最新目录

## 6. 问题四：临时隧道失效 / 外链不稳

### 6.1 典型表现
- 有时能开，有时打不开
- 502 / 504 / timeout
- `/healthz` 偶尔过、偶尔不过
- 你本机能开，别人外网打不开

### 6.2 根因判断
这种情况大概率不是游戏包有问题，而是：
- 隧道服务不稳定
- 本机网络抖动
- 隧道链路对大文件不友好
- 链接已经变更或失效

### 6.3 最快判断法
```bash
curl -fsS https://your-domain/healthz
./tests/smoke/verify_controlled_web_remote.sh https://your-domain
```

如果：
- 本机正常
- 外链 `/healthz` 不稳定
- 线上复验经常失败

那么优先归类成**链路问题**，不是 build 问题。

### 6.4 处理建议
- 不要让用户反复重试同一条坏隧道
- 直接换一条新外链，或切 Pages 备份地址
- 有可控机器时，尽快转成临时 Nginx 静态站

## 7. 故障对照表

| 现象 | 最可能问题 | 先做什么 |
| --- | --- | --- |
| 纯白/黑屏 | wasm MIME / gzip / 缓存头异常 | 跑 `verify_controlled_web_remote.sh` |
| 一直卡加载 | 外链带宽 / gzip 丢失 / 大文件传输慢 | 看卡在哪个阶段，再验 header |
| 像旧版本 | 浏览器旧缓存 / 链路指错目录 | 无痕模式 + 复验缓存头 |
| 时好时坏 | 隧道不稳 | 先测 `/healthz`，不稳就换链路 |
| 本机正常，外链异常 | 代理层或隧道问题 | 不要先怀疑 build |
| 本机也异常 | 本地 build/服务问题 | 重跑 `controlled_web_guard.sh` |

## 8. 向用户收集信息的最小模板
用户反馈异常时，尽量一次收齐下面信息：

```text
1. 链接是否能打开首页
2. 卡在加载第几阶段（1/3、2/3、3/3）
3. 是否看到纯白/纯黑屏
4. 刷新一次后是否变化
5. 无痕模式是否变化
6. 手机型号 / 浏览器 / 网络环境（Wi‑Fi or 蜂窝）
7. 截图一张
```

这样能明显减少“来回追问”。

## 9. 什么时候该停止排查，直接换链路
出现下面任一情况，建议直接切链路：
- 临时隧道 10~15 分钟内反复掉
- `/healthz` 都不稳定
- `verify_controlled_web_remote.sh` 连续失败
- 本机服务正常，但外链层明显吞头或吞 gzip
- 用户侧已经出现大面积无法打开

此时继续在原链路上细修，收益通常很低。

## 10. 备份链路口径
当前旧备份链路：
```text
https://survivor-demo.pages.dev
```

用途：
- 临时外链不稳时的保底方案
- 用于快速判断“问题是在隧道，还是在 build”

注意：
- 它是备份，不是当前主线
- 若主线外链异常，而备份链路正常，优先判断为主线链路问题

## 11. 最终原则

### 原则 1
**先确认是不是链路问题，再怀疑游戏包。**

### 原则 2
**先看 header / gzip / cache，不要只看 200。**

### 原则 3
**先让用户给“阶段 + 截图 + 环境”，不要接受只有一句“打不开”。**

### 原则 4
**临时隧道是验收辅助，不是稳定基础设施。**

---

如果你只想记最关键的排查重点：

1. 黑屏先查 `application/wasm` 和 `Content-Encoding: gzip`
2. 慢加载先看卡在哪个阶段
3. 像旧版本先判缓存，不要先重导出
4. 本机正常而外链异常，优先判隧道/代理层
